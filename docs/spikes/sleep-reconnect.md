# 技術検証：スリープ時の自動接続

検証日：2026-10-07（7章の追加の検証：2026-10-08）
Issue：#26

## 1. 目的

スリープ対応（フェーズ4）の作り方を決めるために、ヘッドホンの自動接続の動きを実機で確かめる。

## 2. 結論

- Mac から切断しても、ヘッドホンが覚えている「最後の端末」は Mac のまま。**ヘッドホンの電源を入れ直すと、Mac につなぎに来る**
- **スリープ中の Mac にもつなぎに来る**。Mac は Bluetooth によってダークウェイク（画面を消したまま一時的に起きる）し、接続を受け付ける
- そのため、スリープ時の切断で手放せるのは「ヘッドホンの電源を入れたまま、他の端末から接続する」場合。ヘッドホンの電源を入れ直すと、スリープ中の Mac に戻る
- MVP は、この Mac だけで完結する範囲なので、この動きは制約として受け入れる。対策は v0.2 以降で検討する（→ 5）
- 実装では、**ダークウェイクのときに再接続しない**ようにする（→ 4）

| 検証 | 結果 |
|---|---|
| ① Mac から切断した後に、ヘッドホンの電源を入れ直すと、どこにつながるか | 最後の端末（この Mac）に自動で再接続された |
| ② スリープ中の Mac に、ヘッドホンの側からつなぎに来るか | つなぎに来た。Mac は Bluetooth によってダークウェイクし、接続を受け付けた |
| ③ 他の端末とつながっているヘッドホンに、Mac から接続するとどうなるか | 見送り（他の端末が関わるので、MVP の範囲外） |

## 3. 検証の環境

| 項目 | 内容 |
|---|---|
| Mac | MacBook Air（M1）、macOS 26.3、バッテリー駆動 |
| 検証に使った機器 | EDIFIER W820NB Plus |
| 確かめ方 | Baton のメニューでの接続状態、電源ログ（`pmset -g log`） |

## 4. 結果の詳細

### 4.1 ① Mac から切断した後に、ヘッドホンの電源を入れ直す

1. Mac から EDIFIER を切断した
2. ヘッドホンの電源を切り、入れ直した
3. → Mac に自動で再接続された

フェーズ1の検証（`docs/spikes/iobluetooth.md` 4.2）では、Mac から切断しただけでは、ヘッドホンは自分からつなぎ直しに来なかった。2つを合わせると、次のように言える。

| 切れ方 | その後のヘッドホン |
|---|---|
| Mac から切断しただけ | 自分からはつなぎ直しに来ない。どこかの端末がつなぎに来るのを待つ |
| Mac から切断した後に、電源を入れ直す | 最後の端末（Mac）に、自分からつなぎに行く |

### 4.2 ② スリープ中の Mac に、ヘッドホンからつなぎに来るか

1回目は、Mac がスリープに入りきる前にヘッドホンの電源を入れたため、スリープしていなかった（電源ログに Sleep の記録がなく、画面が9秒消えただけ）。2回目は、スリープに入ってから30秒以上待って、ヘッドホンの電源を入れた。

```
14:48:20  Sleep      スリープに入った
14:49:01  DarkWake   Bluetooth が理由で、画面を消したまま起きた（wifibt / bluetooth-pcie）
14:49:07  Wake       完全に起きた（ユーザーの操作）
```

- ヘッドホンの電源を入れたタイミング（14:49:01）で、Mac が Bluetooth を理由にダークウェイクし、ヘッドホンが接続された
- スリープ中の Mac でも、ヘッドホンからの接続を受け付ける

### 4.3 そのほかの観察

- スリープを選んでから実際にスリープに入るまでの数秒の間にヘッドホンがつなぎに来ると、スリープに入らないことがある（1回目）
- Mac がスリープしなかった理由を調べるときは、電源ログの Sleep の行と、`pmset -g` の「sleep prevented by」が役に立つ

## 5. 本番の実装への反映

| 反映すること | 根拠 |
|---|---|
| 復帰時の再接続は、ダークウェイクのときではなく、**画面が点いたとき（ユーザーが戻ってきたとき）**に行う。ダークウェイクのときに再接続すると、Mac がまたスリープに戻ったときに、ヘッドホンを掴んだままになる | 4.2 |
| スリープ中にヘッドホンが Mac につないできた場合（4.2）、復帰したときには、すでに接続されている。その機器への再接続は不要（何もしない） | 4.2 |
| 「スリープに入る」の通知の後に、実際には寝なかった場合も、画面が点いたら再接続する | 4.3、`docs/spikes/iobluetooth.md` 4.4 |

## 6. MVP で受け入れる制約と、v0.2 以降の対策の候補

**制約**：スリープ時に切断しても、ヘッドホンの電源を入れ直すと、スリープ中の Mac に接続される。

| 対策の候補 | 内容 | 課題 |
|---|---|---|
| スリープ中に来た接続を、すぐ切る | Baton が「スリープ中」と覚えておき、その間に接続されたら切断する | ダークウェイクの数秒の間に Baton が動けるか。切った後に、ヘッドホンが他の端末に行くかは機種次第 |
| Bluetooth で Mac が起きないようにする | macOS の設定で、Bluetooth 機器によるスリープの解除をオフにする | ユーザーの設定の変更が必要。Bluetooth のキーボードやマウスでも起こせなくなる |
| 他の端末から取り返す | 他の端末の Baton（v0.2）や iPhone アプリ（v0.3）から接続する | 他の端末の対応が必要 |

## 7. 追加の検証（2026-10-08、v0.2 の範囲を決めるため）

4.2 の2回目のダークウェイクが、ヘッドホンではなく Bluetooth のマウスで起きた可能性が出たため、マウスの電源を切り、マウスとキーボードに触らずにやり直した。Baton のログ機能（#30）ができていたので、ヘッドホンがつながった時刻も記録できた。検証に使った機器は EDIFIER W820NB Plus。

### 7.1 結論

- **ヘッドホンの電源を入れると、スリープ中の Mac がダークウェイクし、接続を受け付ける**（4.2 の結論のとおり）。画面は点かない
- **ダークウェイクは約10秒で終わり、Mac はヘッドホンをつないだまま、また寝る**。その間、ヘッドホンは寝ている Mac につながったまま
- **ダークウェイクの間も Baton は動いていて、接続の通知を約0.9秒で受け取れた**。macOS の「システムが起きた」の通知は、ダークウェイクでは届かない（完全に起きたときに届く）

### 7.2 1回目：ヘッドホンが接続したときに、Mac が起きるか

| 時刻 | 出来事 | 記録元 |
|---|---|---|
| 14:40:56 | スリープした（Software Sleep） | 電源ログ |
| 14:41:13 | ダークウェイク。原因は `wifibt` `bluetooth-pcie`。この時刻に、入力機器の操作の記録はない | 電源ログ |
| 14:41:13.877 | EDIFIER がつながった | Baton のログ |
| 14:41:39 | 内蔵の機器の操作で、完全に起きた（ダークウェイクの長さの「26 secs」は、ここまでの時間） | 電源ログ |

### 7.3 2回目：起こさずに放っておくと、どうなるか

| 時刻 | 出来事 | 記録元 |
|---|---|---|
| 14:52:58 | スリープに入る通知。Baton が EDIFIER と EarFun Clip 2 を切断（約1〜1.5秒） | Baton のログ |
| 14:53:04 | スリープした | 電源ログ |
| 14:53:31 | ダークウェイク（原因は 7.2 と同じ） | 電源ログ |
| 14:53:31.909 | EDIFIER がつながった | Baton のログ |
| 14:53:31〜41 | powerd が「機器の準備を待つ」アサーション（`PM configd - Wait for Device enumeration`）を約9秒持っていた | 電源ログ |
| 14:53:41 | また寝た（Maintenance Sleep）。EDIFIER の切断の通知はない ＝ つながったまま寝た | 電源ログ、Baton のログ |
| 14:56:02 | 電源ボタンで起きた | 電源ログ |
| 14:56:04 | ロックを解除。EDIFIER はすでに接続済みなので、Baton は何もしない | Baton のログ |

### 7.4 ダークウェイクの長さ

- Apple は長さを公開していない。powerd が、起きている理由（アサーション）がなくなったら寝かせる
- この Mac の定期の保守のダークウェイクは、多くが2秒、長くて25秒。今回のヘッドホンの接続では約10秒だった
- ログの `SleepService: window begins with cap time=180 secs` は、macOS の保守作業のための上限で、普通のアプリに保証された時間ではない

### 7.5 v0.2 への反映（plan.md フェーズ6）

| 反映すること | 根拠 |
|---|---|
| 離れている間につながってきた登録機器を、Baton が切る。切らないと、寝ている Mac がヘッドホンをつかんだままになる | 7.3 |
| 「離れている間」は、Baton が自分で持つ状態で判断する（ダークウェイクでは「起きた」の通知が届かないため） | 7.1 |
| 切断にかかる時間（通知まで約0.9秒 ＋ 切断約1〜1.5秒）は、約10秒に収まる見込み。足りないときのために、電源のアサーションで寝るのを待ってもらえるかを試作で確かめる | 7.3、7.4 |
| 切った後、ヘッドホンが iPhone に行くか、また Mac に来るかを確かめる。また来る場合に備えて、何度も来たら切るのをやめる安全弁を入れる | 未検証 |
