# Baton 開発計画

最終更新：2026-10-08

MVP（v0.1）の範囲は [mvp.md](mvp.md)、仕様の全体は [spec.md](spec.md) を参照。

## 1. 方針

- **動くものを少しずつ積み上げる**：各フェーズの終わりに、実際に動かして確かめられる状態にする
- **不確かなものから先に片付ける**：仕様全体が成り立つかを左右する IOBluetooth の検証を最初に行う
- **現場と同じ進め方をする**：Issue → ブランチ → 実装・テスト → Pull Request → レビュー → マージ
- **技術の習得も目的にする**：各フェーズに「身につける技術」を設定し、フェーズの終わりに振り返る

## 2. フェーズの一覧

**MVP（v0.1）は、この Mac だけで完結する機能に絞る**（2026-10-07 に見直し。理由は「6. 計画の見直し」）。
**v0.2 も、この Mac だけで完結する機能の磨き込みにする**（2026-10-08 に決定。理由は「6. 計画の見直し」）。

| フェーズ | 名前 | 終わったときにできること | 規模 | 状態 |

```
0 → 1 → 2 → 3 → 4 → 5（v0.1）→ 6 → 7 → 8 → 9（v0.2）
```

他の端末とのやり取り（端末の発見、通信、他の端末の接続状態の表示、他の端末に切断を頼む切り替え など）と iPhone アプリは、時期未定とする（→ 4章の「v0.2 の後」）。

## 3. 開発の進め方（各フェーズ共通）

| 手順            | 内容                                                                          |
| --------------- | ----------------------------------------------------------------------------- |
| 1. 計画         | フェーズの作業を GitHub の Issue に分ける（1 Issue ＝ 1 Pull Request が目安） |
| 2. ブランチ     | Issue ごとにブランチを作る（例：`feature/12-menu-bar`）                       |
| 3. 実装・テスト | BatonKit のロジックはテストを書きながら作る。実機が必要な部分は手で確かめる   |
| 4. Pull Request | 何を・なぜ変えたか、どう確かめたかを書く。自動テストが通ることを確認する      |
| 5. レビュー     | Claude のレビュー（`/code-review`）で指摘を受け、直してからマージする         |
| 6. デモ         | フェーズの終わりに「終わったときにできること」を実際に動かして確かめる        |
| 7. 振り返り     | 身につけた技術、つまずいた点、次に活かすことを短く記録する                    |

### 実装の分担

| 時期 | 担当 | 内容 |
|---|---|---|
| フェーズ0〜1 | Claude | 骨組みと難しい部分を書き、自分で書く部分に `// TODO:` を残す |
| フェーズ0〜1 | 自分 | `// TODO:` の部分を書く |
| **フェーズ2以降** | Claude | **実装をすべて行う**。変更ごとに、設計（責務、データの流れ）とコードを解説する |
| **フェーズ2以降** | 自分 | **コードの理解に時間を使う**。分からない箇所を質問し、Pull Request を読んで内容を確認してからマージする |

- 進め方を変えた理由：書くことよりも、動くコードを読んで質問しながら理解する方が、自分に合っていたため（2026-10-02）
- Issue → ブランチ → Pull Request → マージの流れは、これまでどおり続ける

## 4. 各フェーズの詳細

### フェーズ0：開発の基盤づくり

**ゴール**：以降のフェーズを、現場と同じ流れで進められる状態にする。

| 作業                | 内容                                                                                         |
| ------------------- | -------------------------------------------------------------------------------------------- |
| GitHub のリポジトリ | リモートを作り、push する。`main` への直接の push を禁止し、Pull Request 経由でマージする    |
| CI                  | GitHub Actions で、Pull Request ごとに BatonKit のテストと BatonMac のビルドを自動で実行する |
| テンプレート        | Issue と Pull Request のテンプレートを作る                                                   |
| README              | アプリの概要、ビルド・実行・テストの方法を書く                                               |

**CI の注意点**

- **署名をしないでビルドする**：アプリの署名には Personal Team の証明書が必要だが、証明書は自分の Mac のキーチェーンにしかなく、CI の環境にはない。CI の目的は「コンパイルが通るか」の確認なので、証明書を CI に置くのではなく、署名を省略してビルドする（`CODE_SIGNING_ALLOWED=NO`）。BatonKit のテスト（`swift test`）は、もともと署名が不要
- **Xcode 26 以上を指定する**：BatonKit は `swift-tools-version: 6.2` のため、Xcode 26 以上が必要。CI の設定ファイル（`.github/workflows/`）で、Xcode 26 が入った実行環境（`runs-on:`）と、使う Xcode のバージョン（`xcode-select`）を指定する。使える組み合わせは [actions/runner-images](https://github.com/actions/runner-images) で確認する

**身につける技術**：Git のブランチ運用、GitHub Actions（CI）、macOS の CI 環境

**完了の条件**：テスト用の Pull Request を作ると、CI が走って結果が表示される

### フェーズ1：技術検証（IOBluetooth）

**ゴール**：仕様の前提が実機で成り立つかを確かめ、結果を記録する。検証用のコードは本番に使わない。

| 作業       | 確かめること                                                                          |
| ---------- | ------------------------------------------------------------------------------------- |
| 機器の一覧 | ペアリング済みの機器の一覧（名前、アドレス、接続状態）を取れるか                      |
| 接続・切断 | `openConnection()` で音声（A2DP）まで接続されるか。`closeConnection()` で切断できるか |
| Sandbox    | App Sandbox が ON の状態で、Bluetooth の entitlement を付ければ上の2つが動くか        |
| スリープ   | スリープの前後で、イヤホンの接続がどうなるか                                          |
| 接続の通知 | 接続・切断の通知が届くか（将来のリアルタイム同期の前提）                              |

**身につける技術**：IOBluetooth、Objective-C の API を Swift から使う方法、entitlement と App Sandbox、技術検証の進め方と記録の仕方

**完了の条件**：検証の結果を `docs/spikes/` にまとめ、仕様書 14.1 の該当する項目を更新する。うまくいかない項目があれば、仕様の見直しを判断する

**必要なもの**：この Mac とペアリング済みの Bluetooth イヤホン

### フェーズ2：メニューバーアプリの土台

**ゴール**：アプリの骨組み（常駐、画面の構成、状態の持ち方）を作る。

| 作業                 | 内容                                                                              |
| -------------------- | --------------------------------------------------------------------------------- |
| メニューバー常駐     | `MenuBarExtra` でメニューバーにアイコンを出す。Dock には出さない（`LSUIElement`） |
| アプリの構成         | フォルダ構成、画面と状態の分け方（`@Observable`）を決めて、雛形を作る             |
| ログイン時の自動起動 | `SMAppService` で実装し、メニューからオン・オフを切り替える                       |
| 終了メニュー         | Dock にアイコンがないので、メニューからアプリを終了できるようにする               |

**身につける技術**：SwiftUI の基本、アプリのライフサイクル、`@Observable` による状態管理、Info.plist とビルド設定

**完了の条件**：Baton がメニューバーに常駐し、ログインすると自動で起動する

### フェーズ3：このMacでの機器の管理

**ゴール**：他の Mac のことは考えず、1台の Mac で機器の登録と接続・切断ができる。

| 作業               | 内容                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------ |
| Bluetooth の抽象化 | IOBluetooth を直接呼ばず、プロトコル（インターフェース）越しに使う。テスト用の偽物に差し替えられるようにする |
| 機器の登録と解除   | ペアリング済みの機器から選んで登録する。登録内容は UserDefaults に保存する                                   |
| 接続と切断         | 登録機器を、このMacで接続・切断する                                                                          |
| 表示               | 登録機器の一覧と、このMacでの接続状態を表示する                                                              |
| ダミーのモード     | 環境変数で、本物の Bluetooth の代わりに偽物を使えるようにする（スキーム `BatonMac (Mock)`）                  |

**身につける技術**：プロトコル指向の設計、依存性の注入、Codable と UserDefaults、コールバック型の API を async/await に包む方法、テスト用の偽物（モック）

**完了の条件**：イヤホンを登録し、メニューから接続・切断できる。偽物に差し替えたテストが通る

### フェーズ4：スリープ対応

**ゴール**：Mac がスリープに入るときに登録機器を手放し、復帰したらスリープ前に使っていた機器を取り戻す。他の端末への問い合わせはせず、この Mac だけで判断する。

| 作業 | 内容 |
|---|---|
| 検証 | 次の3つを実機で確かめる（EDIFIER、この Mac、iPhone）<br>① Mac から切断した後、ヘッドホンの電源を入れ直すと、どこにつながるか<br>② スリープ中の Mac に、ヘッドホンの側からつなぎに来るか<br>③ 他の端末（iPhone）とつながっているヘッドホンに、Mac から接続するとどうなるか（失敗する／奪う／2台同時につながる） |
| スリープ・復帰の検知 | `NSWorkspace` のスリープ・復帰の通知を扱う部品を作る。テストのために、プロトコル越しに使う |
| スリープ前の切断 | 接続中の登録機器を切断し、「スリープ前に接続していた機器」として記録する。通知から実際にスリープするまでの約5秒で終える |
| 復帰時の再接続 | 記録した機器に、接続を試す。失敗したら（他の端末で使用中など）あきらめて、記録を消す |
| 寝なかった場合 | 「スリープに入る」の通知の後に実際には寝なかった場合も、復帰の通知で再接続する |
| テスト | 偽物のスリープ・復帰の通知と、偽物の Bluetooth で、切断・記録・再接続の判断をテストする |

**身につける技術**：NSWorkspace のスリープ・復帰の通知、時間の制約がある処理、端のケースの洗い出し

**完了の条件**：
- スリープすると登録機器が切れ、復帰するとスリープ前に使っていた機器が再接続される（実機）
- スリープ中に他の端末（iPhone）でヘッドホンを使い始めていたら、復帰しても奪わない（検証③の結果に合わせて確かめる）
- テストが通る

### フェーズ5：仕上げと受け入れテスト

**ゴール**：この Mac で毎日使える状態にし、v0.1 としてリリースする。

| 作業 | 内容 |
|---|---|
| ログ | `os.Logger` でログを出し、Console.app で調べられるようにする |
| 受け入れテスト | MVP の機能を一覧にしたチェックリストを作り、この Mac で確かめる |
| 不具合の修正 | 受け入れテストで見つかった問題を直す |
| リリース | Release でビルドして「アプリケーション」フォルダに入れ、ログイン時に起動するようにする。`v0.1` のタグを付ける |
| 振り返り | MVP 全体の振り返りと、v0.2 の計画 |

**身につける技術**：ログと不具合の調べ方、テスト計画、Release ビルドと配布、バージョン管理（タグ）

**完了の条件**：受け入れテストのチェックリストがすべて通り、この Mac で1週間使って大きな問題がない

### フェーズ6：離れている間は手放し続ける（v0.2）

**解決する場面**：Mac をスリープさせて離れ、iPhone で使おうとヘッドホンの電源を入れると、寝ている Mac につながってしまう。ヘッドホンは最後につないだ端末につなぎに行き、Mac はその接続でダークウェイク（画面を消したまま一時的に起きる状態）して受け付け、約10秒後にヘッドホンをつないだまま寝る（[検証結果](spikes/sleep-reconnect.md) 7）。ロックしただけでスリープしていない Mac でも、同じことが起きる。

**ゴール**：離れている間（設定がオンのきっかけで離れてから、戻ってくるまで）に登録機器がつながってきたら、Baton が切る。新しい設定は作らず、今の「離れるときに切断」の設定から自動で決める（2026-10-08 に決定）。

| 作業 | 内容 |
|---|---|
| 試作と検証 | ダークウェイク中に切断を終えられるか。切った後、ヘッドホンはどこへ行くか（iPhone に行く／また Mac に来る）。時間が足りなければ、電源のアサーション（`IOPMAssertion`）で寝るのを待ってもらえるか。EarFun Clip 2 でも同じか |
| 離れている状態 | 設定がオンのきっかけが来たら「離れている」にする（そのとき切断する機器がなくても）。戻ってきたら解除する |
| 来た接続を切る | 離れている間に登録機器がつながったら、切断する |
| 戻ってきたら再接続 | 離れている間に切った機器も、「再接続する機器」として記録し、戻ってきたら接続を試す |
| 安全弁 | 同じ機器を切るのは5分間に3回までにして、それを超えたら切らない。「起きる → 切る → また来る」の繰り返しで、Mac とヘッドホンの電池を減らさないため |
| テスト | 偽物の通知で、離れている状態、来た接続を切る判断、安全弁をテストする |

**身につける技術**：macOS の電源管理（ダークウェイク、電源のアサーション）、状態を持つロジックの設計、出来事の順番に関わるテスト

**完了の条件**：
- スリープ中・ロック中にヘッドホンの電源を入れ直しても、Mac につながったままにならない（実機。電源ログと Baton のログで確かめる）
- 戻ってきたら、離れる前に使っていた機器と、離れている間に切った機器が再接続される
- テストが通る

### フェーズ7：出力先の切り替え（v0.2）

**解決する場面**：外部モニター（DELL）につないで作業中に Baton で接続すると、音がモニターから出たままになる。接続する前の出力先がモニターだと、ヘッドホンにつないでも出力先が切り替わらない（[検証結果](spikes/iobluetooth.md) 4.2）。

**ゴール**：Baton が接続したとき（メニューからの接続、戻ってきたときの再接続）に、音の出力先をその機器に切り替える。

| 作業 | 内容 |
|---|---|
| 出力先の部品 | CoreAudio で、出力先の一覧と、今の出力先を扱う。テストのために、プロトコル越しに使う |
| 接続後の切り替え | 接続に成功したら、その機器の出力先を探して切り替える。接続直後は出力先がまだ現れていないことがあるので、少し待つ |
| 検証 | 検証用のアプリで試作した処理（[検証結果](spikes/iobluetooth.md) 4.2）を、実機（DELL のモニター）で確かめる |

**身につける技術**：CoreAudio（C の API を Swift から使う方法）

**完了の条件**：出力先がモニターのときに Baton で接続すると、音がヘッドホンから出る

### フェーズ8：再生中は手放さない（v0.2）

**解決する場面**：音楽や動画を聴きながら画面をロックすると（電源ボタン、自動ロック）、Baton がヘッドホンを切断する。ロックしても再生は続くので、音が Mac のスピーカーに移って鳴ってしまう。

**ゴール**：ヘッドホンから音が出ている間は、ロックと画面の消灯では切断しない（2026-10-09 に決定）。

| 決めたこと | 内容 |
|---|---|
| 効かせるきっかけ | ロックと画面の消灯だけ。スリープでは今までどおり切る（Mac が寝ると音は止まるので、切らないと、音の出ない寝ている Mac がヘッドホンを持ったままになる。再生中は自動のスリープが起きないので、再生中のスリープは自分で寝かせたときか、ふたを閉じたときだけ） |
| 設定 | メニューでオン・オフ。初期値はオン |
| 判定のしかた | CoreAudio で、その機器の出力が動いているか（`kAudioDevicePropertyDeviceIsRunningSomewhere`）。2026-10-09 に、Chrome で再生中に「動いている」と出ることを確かめた |
| フェーズ6との関係 | 再生中なので切断しなかったときは、「離れている間」にしない（まだ使っている最中と見なす） |

| 作業 | 内容 |
|---|---|
| 検証 | 一時停止した後、出力が「動いていない」に変わるまでの時間（Music、Chrome）。外部モニターと電源につないだままふたを閉じたとき、Baton にどの通知が届くか |
| 再生中かの判定 | AudioOutputService に「その機器から音が出ているか」を足す |
| 切断の判断 | SleepHandler が、ロックと画面の消灯のときに、設定と再生中かを見て、切断するかを決める |
| 設定 | AppSettings に追加。メニューにスイッチを置く |
| テスト | 偽物の出力先で、再生中・停止中の判断をテストする |

**身につける技術**：CoreAudio のプロパティ、設定と判断の組み合わせのテスト

**完了の条件**：音楽を聴きながら電源ボタンでロックしても、ヘッドホンで聴き続けられる。再生を止めてからロックすると、今までどおり切断される

### フェーズ9：アイコンと仕上げ（v0.2 のリリース）

**解決する場面**：ヘッドホンがつながっているかを見るのに、毎回メニューを開いている。アプリの一覧で、Baton が標準の絵になっている。

| 作業 | 内容 |
|---|---|
| メニューバーのアイコン | 登録機器のどれかがこの Mac に接続中かを、アイコンで表す（例：つながっていれば塗りつぶし、いなければ線だけ） |
| アプリのアイコン | Icon Composer で作る |
| 受け入れテスト | v0.2 の機能を受け入れテストに足して、この Mac で確かめる |
| リリース | `v0.2` のタグと GitHub の Release |

**身につける技術**：SF Symbols、Icon Composer とアセットカタログ

**完了の条件**：受け入れテストが通り、`v0.2` をリリースする

### v0.2 の後（時期未定）

他の端末とのやり取りは、後回しにする（2026-10-08 に決定）。もう一方の端末はスリープしていることが多く、スリープ中の端末は切断の依頼を受け付けられないため、切り替えの出番が少ない。スリープ時の手放しは、v0.1 とフェーズ6で、この Mac だけで行える。

| 予定の内容 | 元の計画（2026-10-07 の見直し前のフェーズ番号。今のフェーズ6〜8とは別） |
